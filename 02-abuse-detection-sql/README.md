# Abuse detection in SQL

## Business question
Can simple SQL rules flag three kinds of planted abusive accounts in a simulated platform, and how many planted accounts do they catch versus how many legitimate accounts do they wrongly flag?

## Data
Synthetic data generated by a script in this folder, with a fixed random seed. No real user data is used. This is a simulation: results demonstrate SQL rule implementation on planted patterns, not real-world detection effectiveness.

Two tables (SQLite):
- `accounts`: account_id, signup_date, country
- `events`: event_id, account_id, event_time, event_type (login, post, click), ip_address, country

A separate ground-truth file lists which accounts were planted as abusive and which pattern each belongs to. Ground-truth labels are excluded from SQL detection inputs. They are used to evaluate rules and compare thresholds.

Size: about 20,000 accounts and 300,000 events.

## Three planted patterns
1. **Spam ring:** a group of accounts sharing one IP block, posting in short bursts.
2. **Account takeover:** a login from a new country, followed by a sudden jump in activity.
3. **Automated clicking:** accounts generating unusually concentrated click bursts.

Each pattern is made noisy: some legitimate accounts share IPs (offices, households), travel to new countries, or have genuine click spikes, and some planted accounts behave only partly like the pattern.

## Analysis plan
1. Generate the data and ground-truth file.
2. Load the CSVs into SQLite.
3. Write 10 to 12 queries in this order: basic aggregates, joins, a shared-IP self-join, window functions (`ROW_NUMBER`, `LAG`, rolling average), then burst and outlier rules.
4. Combine the rules into one account-level flag per pattern.
5. Score each pattern against the ground truth.

### Historical comparisons
New-country and activity-spike rules use only events preceding the event being assessed. A minimum history requirement, such as at least five prior events, applies. Future activity must not become part of an earlier baseline.

## Evaluation
For each pattern, report:
- Accounts flagged.
- Matching planted accounts caught, expressed as recall.
- Share of flagged accounts with that matching pattern, expressed as precision.
- Legitimate accounts wrongly flagged.

Accounts planted with a different pattern count as false positives for pattern-specific precision. Report wrongly flagged legitimate accounts separately.

Show how precision and recall change when one rule threshold moves, such as the minimum accounts per shared IP block.

## Limitations
- Synthetic data: rules are tested against patterns the generator planted, so results may be optimistic.
- Results are in-sample: the same dataset supports rule development and evaluation, with no held-out set.
- Real abusers adapt, for example by rotating IPs, so fixed rules may lose effectiveness over time.
- Rule thresholds are illustrative, not production values.

## Deliverables
- Data generator script.
- SQL file with the queries, each with a one-line comment.
- Results table per pattern.
- Short README results section.
